# Qwen3-ASR 句末标点驱动的音频游标方案

## 1. 背景

在多人连续交谈场景中，Silero VAD 很难仅通过静音判断句子边界。多人接话、短暂停顿和背景声音会使一段语音持续处于 active 状态，导致当前未定稿音频不断增长，最终形成过长字幕。

Qwen3-ASR 的输出通常已经包含较可靠的句末标点。可以利用连续识别结果中的稳定句末标点提前定稿，并把已经确定的句子对应音频从后续识别窗口中移除，只保留少量重叠音频保护边界。

## 2. 重要限制

当前调用方式为：

```python
result = self.model.transcribe(
    audio=(self._buf, _SAMPLE_RATE),
    language=language,
)
```

当前代码只读取 Qwen 返回的文本，没有逐字或逐词时间戳。因此不能把文本字符位置直接当成精确的音频时间位置。

例如：

```text
第 N 个字 / 总字数 = 音频位置
```

在语速变化、停顿、多人交谈和背景音乐存在时并不可靠。错误的精确裁剪可能切掉句尾文字或下一句话的开头。

因此本方案应采用“稳定文本 + 保守音频边界 + 重叠窗口”，而不是无条件按照字符数删除音频。

## 3. 目标行为

```text
音频块持续进入
        |
        v
Qwen 按 cadence 识别当前未提交窗口
        |
        v
连续结果都包含相同的完整句末标点
        |
        v
提交稳定句子
        |
        +--> 发送 final
        |
        +--> 移除已提交部分的旧音频
             保留句尾 overlap 和之后的新音频
```

例如连续两次识别结果为：

```text
第一次：大家好，今天我们讨论一下这个问题。
第二次：大家好，今天我们讨论一下这个问题。首先，
```

可以提交：

```text
大家好，今天我们讨论一下这个问题。
```

下一轮只重新识别句末附近的 overlap、新出现的音频，以及尚未完成的“首先，”部分。

## 4. 状态设计

Qwen 引擎应维护音频游标和文本提交状态。建议增加或明确以下状态：

```python
_audio_buf                  # 当前尚未完全提交的音频
_audio_base_sample          # _audio_buf 对应的绝对采样位置
_committed_audio_sample     # 已安全提交到哪个绝对采样位置
_committed_text             # 已经输出的文本
_last_raw_hypothesis        # 最近一次完整 Qwen 输出
_hypothesis_history         # 连续多次结果，用于稳定性确认
```

每个输入块应能映射到绝对音频范围，例如：

```text
chunk 1: 0.0s - 0.6s
chunk 2: 0.6s - 1.2s
chunk 3: 1.2s - 1.8s
```

这样提交句子后可以前移音频游标，而不是依赖当前数组长度猜测已经处理了多少音频。

## 5. 句子确认规则

看到一个句号就立即定稿风险较高。建议使用多条件确认：

1. 文本包含 `。！？!?；;` 等句末标点。
2. 该句末标点及其之前的文本在连续 2 次或 3 次结果中保持不变。
3. 句末之后已经出现至少约 200~400 ms 的新音频，避免模型在极短上下文中提前补标点。
4. 句末之前的文本没有继续被 Qwen 修改。
5. 裁剪音频时始终保留约 300~500 ms overlap。

一个 Qwen 结果可能包含多句话，因此不能只判断整段文本的最后一个字符。应扫描文本中的句末标点：已经稳定完成的句子可以提交，最后一个不完整句子继续作为 partial。

## 6. 音频裁剪策略

### 6.1 有时间戳时

如果后续 Qwen3-ASR 或 vLLM 后端能返回逐字或逐词时间戳，应优先使用句末标点对应的时间：

```text
句末标点时间戳
    -> 得到准确的音频裁剪位置
    -> 向前保留少量 overlap
    -> 提交句子并继续接收新音频
```

这是最可靠的实现方式。

### 6.2 当前纯文本接口下

在没有时间戳时，只能根据稳定前缀在完整文本中的比例估算边界：

```python
estimated_boundary = audio_start + (
    len(committed_text) / max(1, len(full_text))
) * len(audio)
keep_from = estimated_boundary - overlap_samples
```

这与当前 `_roll_window()` 使用的比例估算思路相近，但必须满足以下条件：

- 只对连续稳定且以完整句末标点结束的前缀使用；
- 保留足够大的 overlap；
- 不直接丢弃估算边界附近的音频；
- 使用文本去重避免 overlap 造成重复字幕；
- 估算不可靠时宁可多保留音频，不要过早删除。

### 6.3 二次边界搜索

可以在句末附近选择多个候选音频截断点，重新识别短窗口，寻找最早仍能稳定生成该句子的边界。

该方法精度更高，但会额外调用 Qwen，可能加重推理积压，不应作为默认实时路径。

## 7. 与现有 Qwen 引擎的衔接

当前代码已有以下基础能力：

- `_hypotheses`：保存多次识别结果；
- `_stable_prefix()`：提取稳定前缀；
- `_roll_window()`：滚动音频窗口；
- `_remove_committed_overlap()`：处理文本重复；
- `overlap_seconds`：配置音频重叠长度。

目前的主要限制是：

1. 只有达到 `max_window` 后才会滚动窗口。
2. 句末标点只参与静音定稿判断，没有独立触发语义定稿。
3. `_roll_window()` 通过字符比例估算音频边界。
4. `_reset_window()` 会清空 `_committed_tail`。
5. 没有独立的“句子已提交但当前语音会话仍在继续”状态。

建议新增或重构为以下流程：

```text
cadence 到期
    -> 调用 Qwen
    -> 保存完整原始假设
    -> 找到连续结果中的稳定句末前缀
    -> 发送该前缀的 final
    -> 前移音频游标
    -> 保留句尾 overlap
    -> 清理已提交文本的临时假设
    -> 继续当前 VAD 会话
```

语义定稿不应调用完整 `_reset_window()`。完整重置会清除 VAD 活跃状态，并可能把下一位说话人的开头一起丢掉。这里应只清理已经提交的文本状态和旧音频，保留必要的 VAD 状态、尾部 overlap 及新的音频。

## 8. 与 VAD 的关系

句末标点驱动的提交和 Silero VAD 应作为互补信号：

- VAD 负责判断语音开始、长时间结束和是否需要跳过无语音输入；
- Qwen 句末标点负责在持续说话、没有明显静音时提前提交句子；
- 稳定前缀负责降低 Qwen 后续结果改写已提交文本的风险；
- overlap 负责保护音频和文本边界。

推荐的终点优先级：

```text
稳定句末标点 + 最小确认条件
    -> 语义定稿

VAD 连续静音达到 endpoint 阈值
    -> 整段定稿

达到最大窗口但没有安全句末
    -> 仅提交稳定安全前缀，保留未完成后缀
```

句末标点定稿后，VAD 不应被重置为完全静音状态。多人连续交谈时，VAD 仍可能处于 active，需要继续识别后续音频。

## 9. 性能影响

回收已提交句子的音频可以减少：

- 同一句音频被重复送入 Qwen；
- 未定稿窗口持续增长；
- Qwen 输入越来越长导致的推理耗时增加；
- 多人连续说话时字幕句子过长。

但它不能单独解决推理吞吐不足。例如：

```text
cadence = 2.0 秒
单次推理 = 3.6 秒
```

即使句子已经及时回收，只要平均每 2 秒音频仍需要 3.6 秒推理，音频队列仍可能逐渐积压。还需要配合：

- 固定最大识别窗口；
- 句子提交后立即回收旧音频；
- 适当降低识别频率；
- 控制 overlap 大小；
- 必要时切换更快的 ASR 后端。

队列扩容只能延迟丢块，不能解决长期吞吐不足。

## 10. 推荐落地顺序

1. 保留现有 VAD 和 partial/final 接口。
2. 在 Qwen partial 结果中提取稳定的完整句末前缀。
3. 增加独立的语义定稿路径，不等待 VAD 静音。
4. 引入绝对音频游标和音频块边界记录。
5. 先采用保守比例估算，并保留 300~500 ms overlap。
6. 复用现有文本重叠去重逻辑，避免提交重复文本。
7. 语义定稿后只清理已提交部分，不调用完整 `_reset_window()`。
8. 后续如果获得 Qwen 时间戳，再替换比例估算逻辑。

## 11. 结论

可以将 Qwen 输出结果与音频块关联，并在句子确定后不再把该句的旧音频重复输入模型。当前纯文本接口下，音频边界无法做到严格精确，推荐采用：

```text
稳定句末标点
+
音频绝对游标
+
保守边界估算
+
300~500 ms overlap
+
文本去重
```

该方案比单独依赖 Silero VAD 更适合多人连续交谈，同时可以控制 Qwen 输入窗口长度，降低推理积压和队列丢块风险。

## 12. 容忍长句前缀的小幅修正

### 12.1 问题

如果连续结果使用严格的最长公共前缀判断稳定性，长句中的一个字符修正就可能使公共前缀停在句末标点之前：

```text
结果 1：我们今天主要讨论音频缓冲和队列问题。
结果 2：我们今天主要讨论音频缓存和队列问题。
```

此时两次结果虽然都表达了同一个已经结束的句子，但逐字最长公共前缀无法覆盖句末标点，断句逻辑会一直等待。

### 12.2 句子级模糊确认

句末确认不应要求整段文本逐字完全一致。推荐流程：

1. 从最近几次 Qwen 结果中分别提取第一个完整句子；
2. 归一化空白和常见标点差异；
3. 使用编辑距离或序列相似度比较完整句子；
4. 最近结果仍必须包含句末标点；
5. 最近 3 次结果中至少 2 次相似度达到阈值时定稿；
6. 定稿文本使用最新一次完整句子，而不是最长公共前缀。

推荐的保守阈值：

```text
短句：要求完整一致
中长句：相似度 >= 0.90
长度差：不超过 max(2, 句长的 8%)
```

这样可以容忍“缓冲/缓存”这类小幅修正，同时保留最新 Qwen 结果的纠错能力。

### 12.3 无句末标点的长句

如果长句始终没有输出句末标点，还需要使用最大窗口滚动机制。可以将文本划分为：

```text
已确认前缀 | 末尾 8~12 个字的可修订区域
```

只在安全词边界提交可确认前缀，末尾保留 revision window。该路径应继续采用保守边界和 overlap，不能因为一次字符多数投票就直接丢弃音频。

句子级模糊确认解决“已有句末标点但前缀微变”的问题；最大窗口滚动解决“长句一直没有句末标点”的问题，两者不能互相替代。
